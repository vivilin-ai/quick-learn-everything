# 第 6 步 · 学习阶梯

> 依据最近发展区：每一级必须在上一级的一步之内。

## 级别 1 · 完全初学者：看懂循环

1. **应理解**：agent 的本质是「模型 + 工具 + 循环」；workflow 与 agent 的区别；一次工具调用的完整往返
2. **「掌握」的样子**：看到任何 agent 产品描述，**能判断它是 workflow 还是 agent**；能画出一次工具调用的数据流
3. **重点**：工具调用往返、上下文窗口、system prompt / tool definition / tool result 的角色分工
4. **🏁 里程碑**：**能在白板上画出 agent 循环，说清每一步谁在做**
5. **动手**：找一段 agent 原始对话日志，逐条标出哪些是模型生成、哪些是工具返回
6. **⚠️ 常犯错误**：**把 agent 想成「一个更聪明的模型」**而非「模型 + 外部系统的循环」。此误解会让后续所有问题都被归因到模型能力
7. **🚪 自测题**：一次 agent 循环里模型实际被调用几次？工具是模型执行的吗？

## 级别 2 · 基本理解：知道会怎么坏

1. **应理解**：失败模式分类——上下文冲垮 / 工具描述歧义 / 返回不可读 / 循环不终止 / 复合错误累积
2. **「掌握」的样子**：给一个失败案例，**能说出属于哪一类**，而非笼统说「模型不行」
3. **重点**：上下文预算、工具输出格式、终止条件、复合错误率的算术**及其前提**
4. **🏁 里程碑**：**拿到失败日志，能定位到哪一步、哪一类失败**
5. **动手**：把 Day 2 的循环故意弄坏三次（返回超长 / 歧义错误 / 去掉终止条件），记录表现
6. **⚠️ 常犯错误**：**把所有失败归因为「模型不够聪明」**——最贵的错误，导向「等下一代模型」而非「改接口」
7. **🚪 自测题**：单步 90% 串 10 步成功率多少？**若其中 3 步失败无害且可重试，这数字还成立吗？**

## 级别 3 · 实际使用者：能设计工具契约

1. **应理解**：工具签名与工具输出是两个独立设计问题；输出为「被模型读」而设计，非为「被程序解析」而设计
2. **「掌握」的样子**：**能拿已有 API 重新设计成适合 agent 的工具**，并说清每处改动理由
3. **重点**：工具描述写法、输出格式、错误信息可读性、截断/摘要/分页、幂等与重试
4. **🏁 里程碑**：**同一任务，只改工具描述与返回格式（不改模型、不改提示词），成功率明显上升**
5. **动手**：把一个真实 API 包装成 agent 工具，对比包装前后表现
6. **⚠️ 常犯错误**：**原始 API 响应直接丢给模型**；反之——过度加工，把模型需要的信息也删了
7. **🚪 自测题**：工具失败返回 `{"error":"E4012"}` vs `查询失败：仓库不存在，请检查拼写`，对 agent 后续行为影响差别是什么？

## 级别 4 · 问题解决者：能设计边界与接管

1. **应理解**：安全边界（prompt injection、excessive agency）、人在环设计点、权限最小化、可回滚性、责任归属
2. **「掌握」的样子**：给一个业务场景，**能说出哪些环节必须留人签字，以及为什么是这几个**
3. **重点**：信任边界、不可信输入处理、审批点设计、审计日志、blast radius 控制
4. **🏁 里程碑**：**给自己的循环做一次威胁建模**，列出攻击面 + 至少两个可落地缓解措施
5. **动手**：设计带审批点的 agent 流程，明确哪些可自动、哪些必须人工
6. **⚠️ 常犯错误**：**把「人在环」当成加在最后的确认按钮。** 真正的人在环要在不可逆操作之前，**且要给人足够信息做判断**——否则人只会一路点确认。**这正是 Bainbridge 说的那件事**
7. **🚪 自测题**：agent 会读用户上传文档且有权发邮件。攻击者能做什么？**最小改动**是什么能挡住？

## 级别 5 · 自信的实践者：能判断该不该用，并讲得清

1. **应理解**：什么场景**不该**用 agent；维护成本曲线；技能退化的组织后果；长期 TCO 评估
2. **「掌握」的样子**：面对「要不要上 agent」，**能给出有理由的否定答案**；能把整套判断讲给非技术的人听懂
3. **重点**：workflow vs agent 决策树、漂移半衰期、维护成本估算、团队能力建设
4. **🏁 里程碑**：**做一次完整对外分享，能当场回答「什么情况下你不建议用 agent」而不含糊**
5. **动手**：写一份真实业务场景的 agent 可行性评估，**含明确的「不建议」条件**
6. **⚠️ 常犯错误**：**成为 agent 的推销员。** 这一级最大风险不是技术不足，而是投入太多后失去说「这个场景不该用」的能力
7. **🚪 自测题**：团队用 agent 写代码一年后，初级工程师能力会怎样变化？打算怎么应对？

## 当前所在级别（有证据的判断，待用户确认）

**判断：级别 2–3 之间，但路径是歪的。**

证据——做本 skill 的过程本身就是 agent 设计：

- 处理过**上下文预算**（8000 字符上限、progressive disclosure）→ 级别 2 的核心关切
- 处理过**产物漂移**（单一事实源 + `--check`）→ 级别 3 的工程直觉
- 知道**指令要为「被 agent 读」而设计**（英文 description 提升触发率）→ 正是级别 3 的「为被模型读而设计」

**歪在哪**：从「写给 agent 读的东西」这一侧进入，没走过「agent 执行循环」那一侧。所以级别 1 的自测题（模型被调用几次）可能反而答不利索。

**结论**：不是能力问题，是顺序问题。补上级别 1 的循环直觉后会很快跳到 3。

# 第 7 步 · 2 小时啃下核心 20%

> 起点依据第 6 步判断：用户强于「写给 agent 读」、弱于「agent 执行循环」，
> 故前 3 课补循环直觉（级别 1），不从零讲概念。

## 那 20% 是什么

| 概念 | 为什么是核心 |
|---|---|
| **agent 循环的解剖** | 所有失败都发生在循环的某一环。不懂循环，任何故障只能归因到「模型不行」 |
| **上下文是预算，不是容器** | 决定工具输出设计、截断、摘要的全部策略 |
| **工具契约 = 描述 + 输出格式** | 实践者视角的核心，且是**你能改的部分**（模型改不了） |
| **失败模式分类** | 让你能**定位**而非猜。级别 1→2 的分水岭 |
| **信任边界** | 安全理由不随模型变强而消失，是「人在环」长期必要的真正依据 |
| **workflow vs agent 的决策** | 决定「该不该用」，级别 5 的落点 |

**为什么是这六个**：它们都是**钩子**——看到任何 agent 现象都能挂上去。而框架 API、多智能体编排、某模型的特性不是钩子，是这些概念的实例或变体，会过时。

## 10 次课（每课约 12 分钟）

### 课 1 · 循环的解剖
- **目标**：破除「agent = 更聪明的模型」
- **概念**：模型在一轮任务中被调用 N 次；工具由**你的代码**执行
- **练习**：画出循环图，标注每个箭头的执行方
- **资源**：Anthropic《Building effective agents》（免费）
- **结果**：能说清模型与工具的分工

**复习**：1) 循环里模型被调几次？2) 工具由谁执行？3) 模型如何得知工具结果？4) 谁决定循环何时停？5) 去掉循环只留一次调用，还叫 agent 吗？

### 课 2 · 读日志
- **目标**：把抽象循环变成具体文本
- **概念**：tool_use / tool_result 在消息序列里的实际形态
- **练习**：找一段真实 agent 日志，逐条标「模型生成」还是「工具返回」
- **资源**：官方 tool use 文档示例（免费）
- **结果**：看到原始日志不发怵

**复习**：1) 工具结果以什么角色进入上下文？2) 模型「决定调用工具」输出的是什么？3) 调用失败在日志里长什么样？4) 怎么区分模型幻想的调用与真实调用？5) 日志里哪部分每轮都重发？

### 课 3 · 手写最小循环
- **目标**：亲手建立循环直觉
- **概念**：while + 工具分发表，≤100 行
- **练习**：写出来，接 2 个工具
- **资源**：官方 tool use 文档（免费）
- **结果**：**跑通**

**复习**：1) 终止条件写在哪？2) 工具抛异常怎么办？3) 上下文如何累积？4) 如何防无限循环？5) 这段代码里哪部分是「框架」会替你做的？

### 课 4 · 上下文是预算
- **目标**：把上下文当预算而非容器
- **概念**：每轮重发、预算耗尽的表现
- **练习**：**让一个工具返回 5000 行，观察后果**
- **资源**：无需新资源
- **结果**：亲眼见到冲垮

**复习**：1) 冲垮时模型的行为特征？2) 截断该在哪层做？3) 摘要 vs 截断各自代价？4) 为什么长循环比长文档更耗预算？5) 上下文变大，成本与延迟怎么变？

### 课 5 · 工具描述的歧义
- **目标**：体会描述写法的影响
- **概念**：描述是模型唯一的说明书
- **练习**：同一工具写两版描述，对比调用正确率
- **资源**：官方文档的工具定义规范（免费）
- **结果**：**看到只改文字带来的差异**

**复习**：1) 参数名有歧义会怎样？2) 描述该写「做什么」还是「何时用」？3) 两个工具功能相近怎么办？4) 描述过长的代价？5) 怎么知道模型误解了描述？

### 课 6 · 输出为「被模型读」而设计
- **目标**：级别 3 的核心
- **概念**：输出格式 ≠ API 响应格式
- **练习**：把课 3 某工具的返回改成人类可读的简短文本，对比表现
- **资源**：无
- **结果**：能说清两种设计的差别

**复习**：1) `{"error":"E4012"}` 的问题在哪？2) 返回该带哪些上下文信息？3) 什么时候该分页？4) 空结果怎么返回最好？5) 为什么不该把原始 JSON 直接丢给模型？

### 课 7 · 失败模式分类
- **目标**：从「模型不行」升级到能定位
- **概念**：五类失败（上下文冲垮 / 描述歧义 / 返回不可读 / 不终止 / 复合累积）
- **练习**：把课 4/5/6 制造的故障各归类
- **资源**：无
- **结果**：**拿到日志能定位**

**复习**：1) 五类分别是什么？2) 循环不终止属哪类？3) 哪类改接口就能解？4) 哪类只能换模型？5) 怎么最快区分「描述歧义」与「输出不可读」？

### 课 8 · 复合错误率及其前提
- **目标**：学会用它，也学会**质疑它**
- **概念**：0.95²⁰≈36%，以及独立性假设何时不成立
- **练习**：给自己的循环估算成功率，再列三个让乘法不成立的因素
- **资源**：无
- **结果**：能**带前提地**引用这个数字

**复习**：1) 前提是什么？2) 可重试的步骤如何改变计算？3) 「失败无害」的步骤算不算？4) 验证环节如何改变结构？5) 为什么这数字常被滥用？

### 课 9 · 信任边界
- **目标**：补上五视角的结构性遗漏
- **概念**：prompt injection、excessive agency、权限最小化
- **练习**：**给自己的循环做威胁建模**，列攻击面 + 2 个缓解
- **资源**：OWASP Top 10 for LLM Apps（免费）
- **结果**：能说出自己代码的攻击面

**复习**：1) 不可信输入从哪进来？2) excessive agency 具体指什么？3) 为什么模型变强解决不了注入？4) 人在环该放哪个位置？5) 最小权限在 agent 里怎么落？

### 课 10 · 该不该用
- **目标**：级别 5 的落点
- **概念**：workflow vs agent 决策树、维护成本曲线
- **练习**：写出三个**你不建议用 agent** 的场景及理由
- **资源**：回看 Anthropic 那篇 + Bainbridge（免费）
- **结果**：**能给出有理由的否定答案**

**复习**：1) 什么情况 workflow 更好？2) 维护成本曲线怎么估？3) 漂移半衰期为什么重要？4) 技能退化对团队意味着什么？5) 你会用什么问题反问一个说「我们要上 agent」的人？

## 🎯 最终小项目

> 证明「**真的可以上手用**」，不是「理解了概念」。

**做一个 ≤150 行、不用任何框架的 agent**：

1. 接 **3 个工具**，至少一个会返回大量数据（需处理截断）
2. 有 **1 个审批点**，卡在不可逆操作之前，且**给人足够信息做判断**
3. 能**现场演示一次 prompt injection** 及缓解措施

**完成标志**：用它做一次 **15 分钟分享**，当场回答——**「它在什么条件下会坏？」**与**「为什么审批点在那个位置？」**

同时兑现三件事：级别 4 的里程碑、第 5 步一周路径的 Day 7 输出、用户「对外输出/带团队」的真实需求。
