## 第 1 题（初级）· 循环里模型被调用几次

**题目**：2 个工具、顺利完成，模型总共被调用几次？说出数法。
**用户答**：2 次（决策调 tool1 → 收结果决策调 tool2，然后"任务完成即结束"）

| | |
|---|---|
| **分数** | **6 / 10** |
| **答对** | 循环**机制**准确：模型输出调用意图 → 系统执行 → **结果回填** → 模型决定下一步。"回填"是循环心脏，未漏。两次工具决策归属标得准 |
| **确切差距** | **off-by-one，但错的不是算术**。正确为 3 次。暴露问题的是"任务顺利完成即宣告结束"——**系统不知道任务完成了**，它没有理解力，只是分发器。必须把 write_file 的返回再喂模型一次，模型输出**不含工具调用的回复**，系统才能跳出循环 |
| **重讲** | 终止条件不是"工具用完了"，而是**"模型这一轮没有再要求调工具"**。N 次工具调用 → **至少 N+1 次模型调用** |

**追问**：若 write_file 失败（磁盘满），在你的 2 次数法里谁会发现错误？
**用户答**："大模型会返回错误"

- ✅ 方向对，证明修正落进去了
- ❌ **与自己的答案打架**：成立前提是模型还会被调一次。在 2 次数法里第三次不存在 → **错误谁也看不到，静默失败**，用户拿到"已完成"而文件没写成
- ❌ **用词**：工具产生错误 → 系统作为 tool_result 回填 → **模型消费错误并决定怎么办**。模型返回的是决策，不是错误本身。对外讲时这个区分很重要：**错误怎么呈现给模型，是你的事**

## 第 2 题（初级）· 第 5 次调用的输入包含什么

**用户答**：System prompt（角色/准则/工具列表及参数）+ 完整消息序列（user 输入、各轮 assistant 工具调用、各轮 tool 观察结果）+ 最新追加的 tool result

| | |
|---|---|
| **分数** | **8 / 10** |
| **答对** | System prompt 常驻；完整消息序列且**三种角色归属全部标对**；抓住"追加"这个动作；主动补第 3、4 轮假设情形 → 脑子里跑的是**通用循环**而非具体例子 |
| **确切差距 1** | **工具定义的位置**：多数 API 里它是独立顶层参数（`tools=[...]`），不在 system prompt 内。后果是**工具定义每次调用完整重发**，是固定开销——**工具描述长度要乘以循环轮数** |
| **确切差距 2** | 描述了现象但**没点破后果**：**模型是无状态的**，前四轮内容被**重新发送**，不是"记住了" |
| **重讲** | 不是"模型记住了对话"，而是**每次把整本笔记重新念一遍**。它听完就忘，下次还得从头念 |

## 第 3 题（初级，加难度）· search_docs 累积占多少 token

**题目**：每次返回 2000 tokens，跑 10 轮，第 10 次调用时该工具返回内容占多少？
**用户答**：18,000 + 2,000 = 20,000 tokens

| | |
|---|---|
| **分数** | **9 / 10** |
| **答对** | **推理结构完全正确**：旧结果不会消失、全部重发、总量随轮数累加。分解式写法（9 轮累积 + 最新一条）显示他真的在数，不是套公式 |
| **说明** | 严格按"第 10 次模型调用"读应是 18,000（call N 只看得到 1..N-1 的结果）。**但这是我出题时的歧义**（"跑了 10 轮" vs "第 10 次调用"），不算他错 |
| **可带走** | 这个 off-by-one 在真实工程里有意义：**预算估算差一轮就可能撞上限** |

## 第 4 题（中级）· 截断 / 摘要 / 只留最近 3 轮，各自代价 + 何时选 (c)

**用户答**：(a) 断章取义，关键信息常在中后部，致幻觉或反复重试；(b) 额外 LLM 调用增加轮次与耗时 + 摘要损耗，丢掉"当时不重要后来关键"的细节；(c) 灾难性遗忘，前后矛盾或重复劳动。
**选 (c) 的条件**：任务具**马尔可夫性**/阶段性解耦；滑动窗口式工作流（如改 bug 循环，第 10 轮只需第 8–9 轮的变动与报错）；**容错率高且可现查重新校验**。

| | |
|---|---|
| **分数** | **9 / 10**（四题中最好） |
| **答对** | (a) "反复重试"这个后果很多人想不到；(b) 抓到反讽——**为省 token 而多花 token**；"当时看起来不重要、后面决策极其关键"是内行话；**(c) 的选用条件是本题真正答案——删除是否安全取决于信息可不可恢复，他抓住了** |
| **差距 1** | **把 (b) 和 (c) 的风险等量齐观了，但 (b) 更危险**。(c) 失败得吵（信息没了，模型可能发现并重查）；**(b) 失败得安静**——那里有摘要，模型以为还有这个信息，于是不会重查，带着劣化版本继续推理且不知道丢了什么。**看起来还在其实已经坏了，比明摆着没有更难查** |
| **差距 2** | **完全没提缓存——本题最贵的代价**。prompt caching 按前缀匹配；(b)(c) **都在改写历史前缀**，从改动位置往后缓存全部失效，之后每轮重新付全价。(a) 不改历史，前缀稳定，缓存有效。**真实账本可能是反的：省了 token 数，却因缓存失效让花费上升**——一个"优化"把成本做高，生产里非常常见 |
| **重讲** | 判断这三个选项需要**三把尺子**：1) 丢多少信息（答得很好）2) 丢了能不能补回来（答得最好）3) **改写历史的代价**（缓存、可复现、可审计）——第三把还没拿起来 |
