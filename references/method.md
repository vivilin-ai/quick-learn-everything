# 方法论展开

`SKILL.md` 给的是流程骨架。这里是每个阶段的判据、常见失败模式和处理手法。用到哪个阶段读哪一节。

---

## Phase 0 · 澄清目标

### 为什么不能跳过

「学 Kubernetes」这四个字下面藏着完全不同的需求：为面试准备的人需要概念覆盖面和高频考点；为线上救火的人需要的是排障路径和几个关键命令；要做架构选型的人需要的是边界、成本和替代方案对比。三者的学习路径几乎没有交集。跳过澄清直接给路线图，大概率给的是第四种——谁都用不上的通用版。

### 追问技巧

用户说「感兴趣」「想了解一下」时，不要接受这个答案。追问：

> 「假设三个月后你已经学会了，那时候你会拿它做什么具体的事？」

如果用户确实答不上来，说明这是探索性学习。那就把 Phase 0 的验收标准定成「能判断这个领域值不值得我继续投入」，并把整个路径压缩到 2 个里程碑——探索性学习不该一上来就规划 40 小时。

### 挖掘现有基础

不要只问「你会什么」，要让用户**举一个他熟悉的具体例子**。他说「我做过后端」是没用的信息；他说「我用 Django 写过一个订单系统」，你就能拿 ORM 类比状态管理、拿中间件类比拦截器。类比桥梁的质量取决于你对他起点的了解精度。

### 时间预算的作用

时间预算不是用来安慰用户的，是用来**做减法**的。10 小时和 100 小时的路径不是同一条路径的长短版本，而是不同的路径：

- **< 10 小时**：只做 Phase 0–3 + 一轮 Phase 5，目标是「能听懂、能提对问题」
- **10–40 小时**：完整走完七个阶段，3 个里程碑
- **> 40 小时**：完整流程，5 个里程碑，Phase 6 的项目可以做大一些

### 验收标准怎么写

必须是**可检验的行为**，不是感受。

| 不合格 | 合格 |
|---|---|
| 「理解 K8s 的核心概念」 | 「能读懂团队的 Deployment YAML 并独立改出一个新服务」 |
| 「熟悉宏观经济学」 | 「看到一份央行报告，能说出它对我们行业意味着什么」 |
| 「入门机器学习」 | 「能判断一个业务问题该不该用 ML 解，以及大概要什么数据」 |

写完后念给用户听，问「达到这个，你满意吗」。

## Phase 1 · 领域地图

### 模块数量为什么是 5–9

工作记忆的容量限制。超过 9 个模块，用户记不住框架，地图就失去了「让新信息有地方挂」的作用。领域确实庞大时，做两层：顶层 5–7 个，只展开与用户目标相关的那两三个。

### 必须标注的三件事

1. **20/80 边界** —— 哪些模块撑起绝大多数实际场景。新手最大的浪费是在边缘话题上花掉全部预算
2. **争议与流派** —— 哪些问题领域内没有共识。知道「这里有分歧」比记住任何一方的答案更有价值，也是外行装不出来的
3. **与用户已知领域的接口** —— 基于 Phase 0 挖到的基础，指出「这个模块跟你熟悉的 X 是同一回事」

### 常见失败模式

- **地图变成目录** —— 只罗列模块名，不说关系。用户拿到的是书的目录，不是地图。必须说清依赖关系和上下游
- **不敢做减法** —— 什么都标成核心。如果 8 个模块里有 6 个是核心，等于没标
- **抄教材的划分** —— 教材按知识体系组织，实际使用按场景组织，两者经常不一致。按用户的目的场景来划分

## Phase 2 · 术语表

### 三要素

每个术语给：**一句话定义 + 一个类比 + 一个常见误用**。

第三项最容易被省略，但它最值钱。「幂等」的定义谁都能查到，但「很多人以为幂等等于线程安全，其实是两回事」这种信息，只有内行会说。

### 优先收录

- **同一概念的多个叫法** —— 论文叫 A、工程界叫 B、某大厂内部叫 C。不知道这些是一回事，看资料会反复困惑
- **看起来像日常词的术语** —— 「显著」在统计里、「张量」在深度学习里、「弹性」在云计算里，都不是日常含义。这类词最坑，因为用户不会意识到自己不懂
- **缩写** —— 领域内不加解释就用的缩写，列全称

### 持续维护

术语表不是 Phase 2 写完就冻结。后续阶段每碰到新术语就追加。落盘模式下直接改 `glossary.md`；对话模式下每个里程碑结束时给一次增量列表。

## Phase 3 · 精选信源

见 `source-quality.md`，那里有完整的筛选标准和防幻觉规则。

这里只强调一点：**说出你不推荐什么，和推荐什么同样重要**。领域里总有那种流传极广但实际有害的入门资料——过时的、把复杂问题讲得过分简单的、或者只有已入门的人才看得懂却被当作入门推荐的。明确点出来，并说明原因。

## Phase 4 · 学习路径

### 里程碑的构成

每个里程碑四个字段，缺一不可：

| 字段 | 说明 |
|---|---|
| 学什么 | 对应 Phase 1 地图上的哪些模块 |
| 用什么 | 对应 Phase 3 的哪些信源，读哪几章 |
| 产出什么 | 一个能跑的东西、一段能讲清的解释、或一个能做的判断 |
| 怎么算过 | 可检验的判据，不是「感觉懂了」 |

### 排序原则：先能用，再懂原理

让用户在第一个里程碑就获得一次**完整的成功体验**——跑通一个最小例子、做出一个能看见结果的东西。原理留到第二个里程碑再补。

理由是动机管理。自底向上讲原理，用户在获得任何正反馈之前就耗尽了热情。这在自学场景里是首要死因，比内容难度更致命。

### 显式标注可跳过项

对每个里程碑，说清「如果时间不够，这部分可以跳过，代价是 ___」。让用户自己做取舍，比你替他删掉更好——他知道自己缺了什么。

## Phase 5 · 主动学习循环

**这是整套方法里唯一真正产生学习的环节。** 前四个阶段的全部价值，都是为了让这个循环转得更高效。如果时间紧张，宁可压缩 Phase 1–4，也不要压缩这里。

### 四步循环

**1. 讲解** —— 一次只讲一个里程碑的核心概念。讲完就停，不要顺势讲下一个。判断量是否合适：如果你讲的内容用户需要滚动三屏以上，那就太多了。

**2. 复述** —— 让用户用自己的话讲回来。有效的提法：

> 「用你自己的话讲一遍，假设听众是一个完全不懂这个领域的同事。」

**必须真的等用户开口。** 最常见也最致命的失败是：你写了「请复述」，然后紧接着自己给出了一个示范复述。这等于取消了整个环节。写完提问就停止输出。

**3. 诊断** —— 从复述里找漏洞。要找的不是措辞不准，而是三类理解错位：

- **类比用错** —— 用户借用的类比在关键处不成立，会在后面误导他
- **因果颠倒** —— 把结果当原因，或把相关当因果
- **边界缺失** —— 说的都对，但不知道什么时候不成立。这是最隐蔽的一类

**4. 测验** —— 3–5 道题，**场景判断题优先于概念辨析题**。

概念题：「什么是最终一致性？」——能背定义就能答对，测不出理解。
场景题：「用户改了头像，刷新后还是旧的，客服说'等几分钟就好'。这是最终一致性的正常表现还是 bug？为什么？」——必须真懂才能答。

出题时混入 1 道**没有标准答案、需要权衡的题**，看用户会不会考虑取舍。

### 循环规则

- **答错时，先问推理过程再纠正。** 「你是怎么想到这个答案的？」错误的推理链会污染后续所有学习，只改答案等于没改
- **答对时，追问一句「如果条件变成 X 呢」。** 区分真懂和背下来了
- **一个里程碑至少一轮循环。** 用户明显吃力就加一轮，不要为了赶进度往前推——赶完的进度是假的
- **记录薄弱点。** 落盘模式写入 `quiz.md`；下个里程碑开始前，先把上次的错题重考一遍

## Phase 6 · 实践与结业

### 项目设计

- **贴合 Phase 0 的目的场景。** 为面试学的人做一个能写进简历的小东西；为救火学的人做一次模拟排障
- **规模控制在总时间预算的 15% 以内。** 项目太大是自学的第二大死因，用户会卡在中途然后放弃
- **必须有明确的完成标志。** 「做一个博客系统」没有完成标志；「做一个能发文章、能列表、能删除的博客」有

### 不代劳

**这一步最常见的失败模式是你把代码写了。** 用户卡住时，给的是提示、是问题、是缩小范围的建议，不是答案：

- 「你觉得问题出在哪一层？」
- 「先只让这一个函数跑通，其他的注释掉。」
- 「这个报错的关键词是 ___，你搜一下看看。」

### 结业复盘

对照 Phase 0 写下的验收标准，**逐条**判断达标与否。诚实说出没达标的部分——「地图的第 3 个模块你还没真正上手，这块目前只是知道有这么回事」。虚假的结业比不结业更有害，用户会带着错误的自我评估去做决策。

最后给出向前的路：进阶方向、值得加入的社区、该持续跟踪的信息源、以及「下一个自然的学习目标是什么」。
